# ACIES Android wrapper and iOS binary-port feasibility

The Android launcher is thin. The original APK's `MainActivity` contains only an inherited constructor. ACIES's title and game UI, simulation, AI, asset readers, and lobby and multiplayer client code are in `libcdkapp.so`. The APK also supplies the associated XMF data, shaders, textures, sounds, and balance tables. The Android side supplies the platform services that the native game calls. Preserving the original C++ client therefore looks like a compatibility or binary-translation project. [Native symbol inventory](../decrypts/libcdkapp/symbols.demangled.txt) · [Decoded asset schemas](acies-cdk3-xmf-reverse-engineering.md)

The experiments started on November 20, 2026. **Husk reached the original ACIES lobby and opening campaign battle on the Mac and the original title screen on iPhoneW.** A standalone, development-signed app on iPhoneW ran the original CDK startup and frame callbacks and rendered the original ACIES title art. [Mac lobby capture](../captures/ios-port-research/husk-macos-lobby.png) · [iPhone Husk capture](../captures/ios-port-research/husk-iphone/title-and-terms.png) · [iPhone standalone title capture](../captures/ios-port-research/standalone-lifecycle/iphone-w-title.png)

## What starts the game

I decompiled `MainActivity` and `CSView` directly from the original `acies.apk` with JADX. I also compared the extracted ARM64 library against the ZIP entry by SHA-256 and used that byte-identical library for the native audit. The ARM64 ELF is 9,360,160 bytes. Its SHA-256 is `38a37aa8e270015b6c766744763b75c638829edf09373498a11fdf5de33e9ddd`.

1. Android starts `kr.co.brgames.talescraft2.MainActivity`. `CSActivity` loads `cdkapp`, selects a writable storage path, constructs `CSView`, mounts it in a frame layout, and wires lifecycle, keyboard, intents, and notifications. [MainActivity](../acies-apktool/smali/kr/co/brgames/talescraft2/MainActivity.smali) · [CSActivity](../acies-apktool/smali/kr/co/brgames/cdk/CSActivity.smali)
2. `CSView` creates a `GLSurfaceView` renderer and requests OpenGL ES 3 when reported available, with an ES 2 selection otherwise. Its initial `onSurfaceChanged` calls `nativeStart` with logical and framebuffer dimensions, the horizontal and vertical insets, Android's `AssetManager`, and the writable path. Each frame drains queued events and calls `nativeTimeout`. Java also forwards input and lifecycle callbacks. [CSView](../acies-apktool/smali/kr/co/brgames/cdk/CSView.smali) · [Renderer callbacks](../acies-apktool/smali/kr/co/brgames/cdk/CSView$1.smali)
3. `Java_kr_co_brgames_cdk_CSView_nativeStart` at `0x80fd98` initializes files, threading, signals, graphics, and audio, constructs `CSAndroidView`, and enters `onStart(CSView*)` at `0x4f06b0`. That function sets up the view projection and Android services, then loads `Option`, `SortOption`, `Asset`, `LobbyGateway`, and `PVPGateway`, and adds a `LogoLayer`. The first game screen is already native. `Map::update`, `Map::updateAI`, `Unit::updateAction`, `GameLayer::updatePlay`, and `TitleLayer::doAdmission` are further evidence of where the logic lives. [Native symbol inventory](../decrypts/libcdkapp/symbols.demangled.txt)

## What an iOS host must supply

| Boundary | What ACIES actually uses |
| --- | --- |
| Display, input, lifecycle | GL context, drawable and default framebuffer, frame timer, pixel scale and insets, touch pointer IDs, keyboard focus, pause/resume, resize, and graphics context recreation. The iPhoneOS SDK exports all **78** OpenGL ES function names imported directly by the ARM64 library. Context behavior, shader compilation, compressed textures, and device performance still need testing. [CSView](../acies-apktool/smali/kr/co/brgames/cdk/CSView.smali) · [Apple OpenGL ES context guide](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/OpenGLES_ProgrammingGuide/WorkingwithOpenGLESContexts/WorkingwithOpenGLESContexts.html) |
| Files, text and images | Android `AAssetManager` directory and file reads, writable files, Java `CSFont` and `CSRaster`, and `AndroidBitmap` pixel access. The APK's asset directory is already usable as data. The iOS host needs to reproduce how the guest asks for those files and rasterizes its text. [Native binary strings](../decrypts/libcdkapp/rodata-strings.txt) |
| Audio and system APIs | Native CDK uses Java `CSAudio` for Android playback, `CSDevice` for device information, and Java bridges for clipboard, text fields, notifications, WebView and video. Startup also calls SDK extensions for billing, Google Play, Firebase, ads and other services. A local session needs the callbacks expected by the original code even where a third-party service is unavailable. [Native symbols](../decrypts/libcdkapp/symbols.demangled.txt) · [Android audio bridge](../acies-apktool/smali/kr/co/brgames/cdk/CSAudio.smali) |
| Networking and crypto | Native CDK calls into Java `CSURLRequest` and a `HttpURLConnection` worker. `CSCrypto` also delegates operations to Java providers. The native client builds and handles lobby and PvP messages. The existing mock can serve the local game path once the guest network calls reach it. [Request wrapper](../acies-apktool/smali/kr/co/brgames/cdk/CSURLRequest.smali) · [HTTP worker](../acies-apktool/smali/kr/co/brgames/cdk/CSURLConnectionThread.smali) · [Crypto bridge](../acies-apktool/smali/kr/co/brgames/cdk/CSCrypto.smali) · [Local backend](acies-local-mock-backend.md) |
| Guest binary runtime | ELF loading, relocations and constructors, Android Bionic and its C++ runtime, pthreads, JNI objects and callbacks in both directions, and a bridge between Android and Apple calling conventions. The ARM64 export table has **43** named `Java_…` methods across 13 bridge classes, including 15 on `CSView`. That counts Java-to-native entry points only. Native-to-Java calls also pass through the JNI function table, so the ELF import count does not describe the full interface. Sampled functions in the bundled `libandroid.so`, `libEGL.so`, `libGLESv3.so`, and `libjnigraphics.so` contain just `bti` and `ret`. The APK relies on working platform implementations for them. [Android NDK ABI](https://developer.android.com/ndk/guides/abis) · [JNI reference](https://developer.android.com/ndk/guides/jni-tips) · [Apple ARM64 ABI](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms) |

I counted **264** distinct undefined symbols in the ARM64 dynamic symbol table. Eight use Android's `std::__ndk1` namespace, which the iPhoneOS SDK's `libc++.tbd` does not export. Bionic imports also include `__sF`, `__errno`, and checked descriptor helpers. These differences survive an ELF-to-Mach-O format conversion and need translation or compatible implementations. The earlier Xcode test rejected a direct link to the Android `.so`. [Prior link test](acies-ios-preservation-research.md#what-the-android-apk-can-contribute) · [Apple code signing](https://support.apple.com/guide/security/app-code-signing-process-sec7c917bf14/web)

## Two ways to preserve the original binary

**Husk compatibility test.** Husk is an existing iOS app that handles Android native libraries, graphics, input, and parts of the Java framework. The project's releases include a mode that converts and signs guest libraries without JIT for compatible games. ACIES provides the ARM64 library that path expects. CDK uses a regular activity with its own `GLSurfaceView`, and I found no ACIES or CDK regression case in Husk's source. Success depends on whether the generic Java activity path can start `CSActivity`, load `cdkapp`, supply the asset manager, and drive its renderer. A desktop harness can identify the first missing class or callback before a device test. [Husk repository](https://github.com/Leviidev/Husk) · [Husk releases](https://github.com/Leviidev/Husk/releases) · [Husk regression cases](https://github.com/Leviidev/Husk/blob/main/tools/regress/cases.txt)

**Standalone signed iOS build using ahead-of-time translation.** A translator can turn the shipped Android code into code compiled and signed for iOS, with a game-specific host that supplies the remaining Android services. `androidrecomp` documents a desktop demonstration of ARM64 lifting using an Android game with the same broad native-engine architecture. `droidlift` documents one on-device iOS port using ahead-of-time translation of ARMv7 and a per-game host profile. ACIES also ships ARMv7, though the ARMv7 ELF links `libGLESv3.so` and droidlift's documented renderer support is GLES 2. Neither project establishes ACIES support. A standalone ACIES port needs import and JNI coverage, stable lifecycle and rendering, plus a test with the original assets and the local backend. [androidrecomp](https://github.com/sp00nznet/androidrecomp) · [droidlift](https://github.com/thedankest/droidlift)

### Husk test results

- Husk 3.4's scanner classified `acies.apk` as a generic Java activity with native code. It identified three DEX files, 264 native imports, and 57,097 relocations in the engine, with zero unsupported relocation types. Its `elf2macho-test --prepare` converted all 17 ARM64 libraries from the APK to Mach-O dylibs. [Husk 3.4 source](https://github.com/Leviidev/Husk/tree/acfd7bcb6d1d2f6655a24e43d1d6f87cf142667a)
- The stock Mac harness launched `MainActivity`, ran the engine's 22 static constructors, completed `JNI_OnLoad`, created an OpenGL ES 3 context, and called `CSView.nativeStart` from the GL thread. It crashed in `ndk_is_icu_function_available` during `CSGraphicsImpl::initialize`. Six `gz*` zlib imports also remained unresolved at that point.
- A temporary host patch mapped Android's legacy ICU lookup to the APEX ICU bundled with the harness and supplied the six zlib imports. With that patch, the original APK booted through the generic Java activity path with `TL_NO_XMEM=1` and `TL_AOT_NO_ALIAS=1`. The original title screen displayed version **2.5.1.338.0**. The original APK ran with network access denied for this test. [Local screenshot](../captures/ios-port-research/husk-macos-title.png) · [Local host patch](../captures/ios-port-research/husk-3.4-legacy-icu-zlib.patch) · [Local reproduction script](../captures/ios-port-research/run-acies-husk-mac.sh)
- A second run used the checkout's `acies-lan.apk`, whose ARM64 CDK binary matches the original, and routed the APK's two local test ports to a private loopback mock. The harness posted to admission and login, accepted guest input, displayed the original lobby and advanced its first-run tutorial. The mock captured post-login requests including `pvp-server`, `ping`, `game/prev-result` and `tutorial/step`. The sandbox permitted only the mock's loopback ports. The harness exited cleanly after 7,755 frames. ### Standalone translation test results

- Using `androidrecomp` at `4a2004953e396fca04e940c300cad7c9f5fa77f3`, the lifter produced C for **24,305** function extents across `libcdkapp.so` and the APK's `libc++_shared.so`, covering **1,076,670** decoded instructions with zero generated trap stubs. Xcode's iPhoneOS 27.2 SDK built all **130** generated C files for ARM64 and assembled a **54,010,856-byte** static archive. The archive needs the translation runtime and resolved host APIs to run. Emission counts measure coverage of decoded instructions and discovered extents. [Pinned androidrecomp source](https://github.com/sp00nznet/androidrecomp/tree/4a2004953e396fca04e940c300cad7c9f5fa77f3)
- Two real exports, `CSMath::sqrt(unsigned int)` and `CSBuffer::readLength()`, were also built into a small native iPhone app. On the Mac, the lifted functions matched Unicorn executing the original Android instructions on **8,759** square-root inputs and **3,212** length and cursor cases. On iPhoneW, the development-signed iPhoneOS Mach-O process printed `ACIES_BINARY_PROBE PASS sqrt=7 length=5`. [Local differential probe](../captures/ios-port-research/verify-lifted-primitives.py) · [Local iPhone probe source](../captures/ios-port-research/AciesBinaryProbe.m)
- The translated engine, translated NDK C++ runtime, and host runtime linked together into an iPhoneOS ARM64 Mach-O. In a separate network-denied Mac run, the host mapped the original ELF sections as data, applied **57,097** engine relocations and **3,873** C++ runtime relocations, ran the **22** translated ACIES static constructors, and returned **`0x00010006`** from the translated `JNI_OnLoad`. This exercised startup before Android's `CSView.nativeStart` callback.
- A development-signed build on iPhoneW repeated the startup check and provided the Android `AAssetManager` calls through the host runtime. It reported **zero unresolved imports** and used the original translated `CSFile` routines to read **38,576 bytes** of `assets/version.xmf` and seek to offset 17 for a 127-byte read. Both reads matched the original package bytes. The original ELF files are data resources inside the app. iOS executes the signed Mach-O translated code. **Acies Binary Probe**, build 3, is installed on iPhoneW with this test. ### Where CDK3 helps

The public CDK3 tree gives us the shape of an iOS host, including UIKit startup, an `EAGLContext` and `CADisplayLink`, bundle files, touch events, audio, and Foundation networking. The iOS SDK compile probe used `-DCDK_IOS -DCDK_IMPL` with the shipped headers. It failed to compile `CSAppDelegate.mm` and `CSIOSView.mm` because `CSView.h` is missing. The URL bridge and buffer tests hit unresolved identifiers in the shared `CSArray.h`. The iOS delegate still calls `onStart(CSView*)`, while the current engine header declares `onStart()`. This source snapshot would require repairs to build. It also lacks the original game code, and some of its asset readers diverge from those in the shipped client. Reusing its iOS patterns can help implement a host for the preserved binary. [CDK3 iOS platform source](https://github.com/56-13/CDK3/tree/57cdd85da2f6022c983b327c1fe4348c4809841a/client/src/CDK/Sources/Platform/ios) · [CDK3 application interface](https://github.com/56-13/CDK3/blob/57cdd85da2f6022c983b327c1fe4348c4809841a/client/src/CDK/Sources/Interface/CSApplication.h) · [Asset format comparison](acies-cdk3-xmf-reverse-engineering.md)

## Standalone LAN 1v1

On November 20, 2026 UTC, iPhoneW and a OnePlus N100 paired through the
private Mac mock gateway using separate synthetic guest profiles. The iPhone
build ran the translated CDK game in UIKit. The Android side used a separate
test install with the original CDK binary. The updated host supplied the
Android service callbacks that had stalled guest login, the secure HTTP API
bridge, and the Darwin TCP adapter used by the original gateway client.
[Host source and build instructions](../tools/acies_ios/README.md)

Both clients reached ready in the first match. The iPhone aborted as play
started while a translated CDK array destructor was freeing memory. The same
match loaded in either seat on the Mac. The second physical attempt loaded
the original battlefield on both phones, including their starting bases and
workers, and both clocks read 07:11 when the Build menu was opened on iPhone.
The allocator abort remains intermittent. The diagnostic build records guest
stack frames and ownership information if the invalid free recurs.

## Community account iPhone variant

A separate unsigned build adds Sign In, Sign Up, and Keychain-backed Continue.
The macOS fixture verified registration, sign-in, session restoration, and
admission and login in the translated client against a local account service.
The signed iPhone needs its own account test. The community gateway also
needs a trusted TLS connection for the original client's TCP traffic. The
physical LAN match used guest profiles and direct private TCP.
